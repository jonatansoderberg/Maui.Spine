## 1. Outbound-only transports from the home to Azure (SignalR Service, Web PubSub, Relay Hybrid Connections, IoT Hub, Event Grid MQTT, Service Bus)

### Takeaway
All six options work outbound-only over 443 behind CGNAT, but they differ sharply in what they give for free: **Relay Hybrid Connections** gives true synchronous HTTP request/response to the home (502 immediately if the home is offline), **IoT Hub direct methods** and **Event Grid MQTT v5** give built-in device RPC with timeouts, while **SignalR Service (serverless)** and **Web PubSub** give cheap fan-out of live state to many app clients but need a hand-built correlation/rendezvous for cloud→home RPC. ASP.NET Core SignalR "client results" (`ISingleClientProxy.InvokeAsync<T>`) is the only RPC-to-a-specific-client primitive among the realtime services, and it requires a hub server (Default mode), not Functions. For a household, Web PubSub (or SignalR) for the state stream plus a command pipeline with correlation ids is the best fit; IoT Hub and Service Bus are poor fits for app fan-out.

### Cited Findings

**Azure SignalR Service — modes and routing**
- Three modes: Default, Serverless, Classic; Classic is for backward compatibility only ("Don't use Classic mode except as a last resort"). — [concept-service-mode.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/azure-signalr/concept-service-mode.md)
- Default mode: hub server and clients both connect to the service, which acts as a proxy; server connections are WebSockets from hub server to service; a client "sticks" to one hub server for its lifetime. — [concept-service-mode.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/azure-signalr/concept-service-mode.md)
- **Default mode: "a client cannot connect without a hub server being connected to the service first"**; if all hub servers disconnect, clients get "no server is connected" errors and routed connections drop. — [concept-service-mode.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/azure-signalr/concept-service-mode.md)
- Serverless mode: no hub server; server-side pushes via REST API (one-off) or a WebSocket from the Management SDK ("persistent"); client→server messages and connect/disconnect events are delivered to **upstream endpoints** (webhooks), which "can only be configured in Serverless mode". — [concept-service-mode.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/azure-signalr/concept-service-mode.md), [concept-upstream.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/azure-signalr/concept-upstream.md)
- Upstream URL template supports `{hub}`, `{category}` (connections/messages), `{event}`; a Functions SignalR trigger exposes `<Function_App_URL>/runtime/webhooks/signalr?code=<API_KEY>`; Key Vault references (`{@Microsoft.KeyVault(SecretUri=…)}`) with managed identity can hide the key in the URL; secrets reread every 30 minutes. — [concept-upstream.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/azure-signalr/concept-upstream.md)
- "SignalR Service doesn't support the `StreamInvocation` message from a client in Serverless Mode." — [signalr-concept-serverless-development-config.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/azure-signalr/signalr-concept-serverless-development-config.md)
- Functions isolated worker supports a class-based model: hub class derives from `ServerlessHub` / `ServerlessHub<T>` (strongly typed), registered with `.AddServerlessHub<Functions>()`, exposing `Clients`, `Groups`, `UserGroups`, `ClientManager` and `NegotiateAsync`; docs note the isolated class-based model "doesn't optimize how you write SignalR triggers due to the limitation of C# worker model". Sample: `AzureSignalR-samples/samples/DotnetIsolated-BidirectionChat`. — [signalr-concept-serverless-development-config.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/azure-signalr/signalr-concept-serverless-development-config.md), [functions-bindings-signalr-service-trigger.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/azure-functions/functions-bindings-signalr-service-trigger.md)
- Management SDK (`Microsoft.Azure.SignalR.Management`): `ServiceManager` → `CreateHubContextAsync` (expensive, reuse per hub) → `ServiceHubContext` for sending, groups and `NegotiateAsync(new(){UserId=…})`; usable from console apps, Functions or web servers. — [signalr-howto-use-management-sdk.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/azure-signalr/signalr-howto-use-management-sdk.md)
- **Client results (ASP.NET Core SignalR ≥ 7):** server calls `Clients.Client(connectionId).InvokeAsync<T>("Method", cancellationToken)` (or via `IHubContext<T>`, or strongly typed `Hub<IClient>` returning `Task<T>`); the .NET/TS client returns the value from its `.On(...)` handler; docs use a 30-second `CancellationTokenSource` as the timeout; not allowed from `OnConnectedAsync`/`OnDisconnectedAsync`. — [AspNetCore.Docs hubs.md](https://github.com/dotnet/AspNetCore.Docs/blob/main/aspnetcore/signalr/hubs.md)
- ASP.NET Core SignalR client feature table lists Client Results supported from server 7.0.0 and .NET/JS clients 7.0.0 (Swift client 1.0.0-preview.1); page dated 08/25/2026. — [AspNetCore.Docs client-features.md (via search)](https://github.com/dotnet/AspNetCore.Docs/blob/main/aspnetcore/signalr/client-features.md)
- SDK status: `Microsoft.Azure.SignalR` 1.32.0 removed .NET 6; supported TFMs .NET 8 and .NET 9; packages include `Microsoft.Azure.SignalR.Management`, `.Serverless.Protocols`, `.Emulator` (net8.0). — [Azure/azure-signalr README](https://github.com/Azure/azure-signalr/blob/dev/README.md). A stable `Microsoft.Azure.SignalR@1.33.1` was listed on 14 Oct 2026. — [azure-signalr-client-e2e release](https://github.com/Azure/azure-signalr-client-e2e/releases/tag/stable-20261014-004030)

**Azure Web PubSub**
- Same unit model as SignalR: Free 20 connections / 20,000 messages/day; Standard/Premium_P1 1,000 connections/unit, 1,000,000 included messages/unit/day, up to 100 units (P2 100–1,000). — [azure-web-pubsub-limits.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/includes/azure-web-pubsub-limits.md)
- Billing: units billed by seconds of use, daily; message = 2 KB of **outbound** traffic; outbound includes messages to receivers **and messages sent to upstream webhooks** and live-trace logs; inbound (client→service, server→service) is free; example: 4 KB to Functions + 4 KB × 10 receivers = 44 KB = 22 messages. Instances can have 1, 2, 5, 10, 20, 50 or 100 units; plan ≤80% utilisation. — [concept-billing-model.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/azure-web-pubsub/concept-billing-model.md)
- Price: Azure China lists Standard ¥9.66/unit/day, Premium ¥12.72/unit/day, extra ¥6.36 per million — [azure.cn pricing (via search)](https://azure.cn/en-us/pricing/details/web-pubsub/index.html). Official US/EU prices not readable.
- `json.webpubsub.azure.v1` subprotocol ("PubSub WebSocket client"): join groups, publish directly to a group "without a round trip to the upstream server", streaming to a group (`streamSequenceId`, `streamAck`/`streamNack`/`streamClosed`), and custom `event` requests routed to upstream event handlers; requests with `ackId` get an `ack` response — client must implement its own await + timeout. — [reference-json-webpubsub-subprotocol.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/azure-web-pubsub/reference-json-webpubsub-subprotocol.md)
- Reliable subprotocols `json.reliable.webpubsub.azure.v1` / `protobuf.reliable.webpubsub.azure.v1`: on reconnect the client reuses `connectionId` + `reconnectionToken` (`wss://…/client/hubs/<hub>?awps_connection_id=…&awps_reconnection_token=…`) to restore the session without re-negotiating; recovery is abandoned if failures continue for more than 1 minute; the Client SDK uses the JSON reliable protocol by default. — [howto-develop-reliable-clients.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/azure-web-pubsub/howto-develop-reliable-clients.md)
- Client events: `connect` and user `message`/custom events are **synchronous (blocking)** — the event handler can authenticate, set `userId`/roles, or reply; `connected`/`disconnected` are asynchronous notifications. Max WebSocket frame **1 MB**. Roles: `webpubsub.joinLeaveGroup[.<group>]`, `webpubsub.sendToGroup[.<group>]`, plus wildcard `webpubsub.joinLeaveGroups.<pattern>`. — [concept-service-internals.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/azure-web-pubsub/concept-service-internals.md)
- Functions: `WebPubSubConnection` input binding (negotiate), `WebPubSubTrigger` for service events; the trigger "supports return value in synchronize scenarios" (`UserEventResponse`, e.g. `request.CreateResponse(BinaryData.FromString("ack"), WebPubSubDataType.Text)`) — i.e. client→Function request/response is native. — [reference-functions-bindings.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/azure-web-pubsub/reference-functions-bindings.md)
- Event-handler webhooks are validated with CloudEvents abuse protection (OPTIONS to `…/validate`). — [howto-develop-eventhandler.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/azure-web-pubsub/howto-develop-eventhandler.md)
- **MQTT in Web PubSub is Preview**, MQTT over WebSocket only, "lightweight adaptation": no wildcard subscriptions, no retained messages, no shared subscriptions, no topic alias; Microsoft points to Event Grid for a full broker. — [overview-mqtt.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/azure-web-pubsub/overview-mqtt.md)
- Web PubSub for Socket.IO: managed Socket.IO without an adapter, ">100,000 client connections out of the box", ">99.9 percent uptime". — [socketio-overview.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/azure-web-pubsub/socketio-overview.md)

**Azure Relay Hybrid Connections**
- Exposes on-prem services "without opening a port on your firewall"; based on HTTP and WebSockets; listener holds an outbound control channel; works with any WebSocket library; WCF Relay is the legacy offering. — [relay-what-is-it.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/azure-relay/relay-what-is-it.md)
- HTTP request/response over the control channel: bodies ≤ **64 kB**, headers ≤ 32 kB; larger requests/responses must be upgraded to a "rendezvous" WebSocket. Listener sends **Renew** (replace SAS token before expiry; expiry drops the control channel but not ongoing connections) and **Ping** (keeps NAT/load balancers from dropping; failed ping → reconnect). Listener token needs **Listen** right; sender token (query `sb-hc-token` or `Authorization`) needs **Send**. — [relay-hybrid-connections-protocol.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/azure-relay/relay-hybrid-connections-protocol.md)
- **No active listener → 502 Bad Gateway; listener not handling → 504 Gateway Timeout after 60 seconds.** — [relay-hybrid-connections-protocol.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/azure-relay/relay-hybrid-connections-protocol.md)
- .NET Standard API `Microsoft.Azure.Relay`: `HybridConnectionListener`, `AcceptConnectionAsync()` → `HybridConnectionStream`, plus an HTTP `RequestHandler` mode. — [relay-hybrid-connections-dotnet-api-overview.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/azure-relay/relay-hybrid-connections-dotnet-api-overview.md)
- Pricing: charged per listener unit with 5 GB data/month included (pooled), overage per GB — [Azure Relay FAQ / Service Bus pricing (via search)](https://learn.microsoft.com/en-us/azure/azure-relay/relay-faq). A third-party page gives £8.061 per listener/month and £0.825/GB overage (UK, possibly dated) — [chakray.com (via search, unverified)](https://chakray.com/?p=37683).

**Event Grid namespaces — MQTT broker**
- MQTT v5 and v3.1.1: Last Will and Testament, **request-response with response topic + correlation id** (v5), clean start/session expiry, persistent sessions, **MQTT Retain** ("devices instantly receive the latest known state"); QoS 2 not supported. Routing to Azure services/webhooks; **HTTP Publish** lets apps (e.g. Functions) publish MQTT messages with an HTTPS POST and no MQTT session. - **State-stream math:** 10 HA state changes/s = 864,000/day; forwarded unfiltered to 3 app clients ≈ 2.6 M outbound messages/day → 1 Standard unit (1 M/day included) plus ~1.6 M/day overage on SignalR or Web PubSub. With "subscribed entities only + per-entity throttling/deadband + only while the app is in the foreground", the realistic volume falls well under 1 M/day, so one Standard unit with no overage is the expected bill. The Free tier (20,000 messages/day ≈ 0.23 msg/s, 20 connections) is dev-only. On IoT Hub, 864k D2C/day exceeds one S1 unit (400k/day) and IoT Hub still cannot push to phones — it needs a second realtime service, so it is a poor fit.
- **Web PubSub over SignalR for this system:** (1) the connector can publish state directly to a per-home group with a scoped role (`webpubsub.sendToGroup.home.<id>.state`), so state fan-out costs one billed message per receiver and **no Function execution**, whereas SignalR serverless needs an upstream→Function→`Groups.SendAsync` hop (billed twice and one Function execution per state change); (2) ESP32 and Android TV can use a plain JSON WebSocket (or MQTT-over-WS in preview) instead of implementing the SignalR handshake/record-separator protocol; (3) synchronous user events give connector→cloud request/response natively. SignalR wins only if you want `InvokeAsync<T>` client results, which require a Default-mode hub server (always-on ASP.NET Core app), not Functions.
- **Making the connector itself the Default-mode hub server** (ASP.NET Core on the Pi with `AddAzureSignalR()`, outbound WebSockets) is technically possible and gives full SignalR semantics with no cloud compute, but: clients cannot connect at all while the home is offline (documented), there is no cloud-side cache, and the hub server needs the resource-wide SignalR access key/identity — unacceptable for multi-home. Treat as a single-home hack only.
- **Relay Hybrid Connections** is the simplest way to get synchronous "call the home" semantics from stateless Functions and the AI server (plain `HttpClient` to `https://<ns>.servicebus.windows.net/<home-id>/…` with a Send SAS; immediate 502 when offline), and per-home hybrid connections with per-entity Listen/Send SAS give natural tenant isolation. It does not fan out state, so it would be a second link next to Web PubSub/SignalR. Good fit for request/response reads (device lists, history) and as a fallback; overkill as the only channel.
- **Event Grid MQTT** is the strongest "single fabric" alternative: MQTT 5 request-response for commands, retained messages as a free last-known-state cache per entity topic, LWT for presence, JWT/webhook auth for app users, native ESP32 support, HTTP Publish from Functions. Downsides: no SignalR-style .NET client experience for MAUI (use MQTTnet), topic-space/permission modelling work, TU pricing not verified, 64 KB in-flight limit.
- **Service Bus** fits only as internal cloud plumbing (e.g. durable command queue); not for client fan-out or low-latency push.
- **Recommended architecture (v1, single household, multi-home-ready):**
  - **Azure Web PubSub Standard S1 (1 unit; Free for dev)** with two hubs: `connectors` (one connection per home, userId `connector:<homeId>`) and `clients` (MAUI, ESP32, TV; userId = user id, groups `home.<homeId>.state.*`).
  - **Azure Functions Flex Consumption, .NET 10 isolated** for REST (`/homes/{id}/entities`, `/commands`, `/dashboards`), `negotiate` endpoints (issue Web PubSub client URLs/tokens with least-privilege roles), and Web PubSub event handlers (connect auth, connector presence, command results, snapshot updates).
  - **Commands:** API validates → policy check → writes command row (idempotency key) → `SendToUserAsync("connector:<homeId>")` → connector executes on HA → replies with a synchronous user event (`commandResult`) → handler updates the row and pushes the result to the requesting user's connections. API returns 202 + commandId by default; synchronous callers (AI tool calls) wait a bounded time (e.g. ≤8 s) on the row.
  - **State:** connector publishes coalesced deltas straight to `home.<homeId>.state` groups and periodically (debounced) upserts a snapshot through the API to Table Storage; apps read the snapshot over REST first, then subscribe.
  - **Optional second link:** Relay Hybrid Connection per home for large/synchronous reads (history, camera snapshots) if Web PubSub's 1 MB frame or async pattern becomes awkward.
  - **Alternative if the AI server is an always-on ASP.NET Core app anyway:** host a Default-mode SignalR hub there and use `Clients.Client(connectorConnId).InvokeAsync<CommandResult>(…, cts(10 s))` for true RPC; apps connect as SignalR clients.

## 2. Non-Azure alternatives (Cloudflare Tunnel, Tailscale/Funnel, ngrok, Nabu Casa) — when are they better than building it?

### Takeaway
Tunnels expose the home's own HTTP/WebSocket API with near-zero code and are better when the only consumers are the owner's own apps/devices and you accept the home as the single source of truth (no cloud cache, no offline reads). They don't provide per-user/per-scope authorization of commands, an audit log, a cloud-side state projection, or multi-home tenancy, which the AI server and a future multi-home product need. Nabu Casa exposes the full HA UI/API (which means HA credentials end up in clients), against the "never send the HA token to the cloud" rule.

### Cited Findings
- Cloudflare WebSockets are available on Free, Pro, Business and Enterprise plans; Free-tier concurrency is described only as "Low"; community reports of 503s around ~14k open WebSockets on Free (anecdotal). — [Cloudflare WebSockets docs (via search)](https://developers.cloudflare.com:2053/network/websockets), [Cloudflare community (via search)](https://community.cloudflare.com/t/websocket-limits/56946)
- A secondary source states tunnels have no traffic cap, a limit of 1,000 tunnels per account and 100 active connections per tunnel to the edge; Cloudflare Zero Trust (Access) free plan supports up to 50 users (requires payment details but isn't charged). — [DEV Community (via search, secondary)](https://dev.to/realchaika/how-to-setup-a-cloudflare-tunnel-on-linux-40d9)
- Tailscale Funnel: listens only on ports 443, 8443 and 10000; TLS only; hostnames under the tailnet's `*.ts.net` domain; traffic "subject to non-configurable bandwidth limits"; only on platforms that run the Tailscale CLI; a port can't be used for Serve and Funnel at the same time; Funnel described as beta. — [Tailscale Funnel docs (via search)](https://tailscale.com/kb/1223/tailscale-funnel)
- Nabu Casa (Home Assistant Cloud): £6.50/month or £65/year incl. VAT on Nabu Casa's page; EU €7.50/month or €75/year per an October 2026 article; Home Assistant Cloud is being renamed **Home Assistant Link** with HA 2026.12 (2 Dec 2026), features and price reportedly unchanged; remote access needs no port forwarding. — [nabucasa.com/pricing (via search)](https://www.nabucasa.com/pricing/), [smarthomeassistent.de (via search)](https://www.smarthomeassistent.de/home-assistant-cloud-wird-umbenannt/), [home-assistant.io/cloud (via search)](https://www.home-assistant.io/cloud/)

### Inferences
- **Tailscale (no Funnel)** is the best zero-code option when every client can run Tailscale (MAUI iOS/Android/Mac and Android TV can; the ESP32 realistically cannot), and the AI server can join the tailnet; it keeps the home API private. Funnel adds public reach but with bandwidth limits, beta status and fixed ports — fine for webhooks, not for a product API.
- **Cloudflare Tunnel + Access service tokens** is the best "public HTTPS + WebSocket to the connector" without Azure: the Pi runs `cloudflared` outbound; Access gates requests. Better than building it if the goal is only remote access for one household. It still leaves auth/authorization, offline cache and push notifications to the connector.
- **Nabu Casa / Home Assistant Link** is best for "remote HA UI + Alexa/Google" for the owner; it is not a substitute for a Spine-branded multi-client API with scoped tokens, and it requires HA long-lived tokens on clients.
- **Build on Azure** when you need: cloud-held state for offline reads, per-user/per-scope policy (locks/alarm step-up), audit, AI server integration with stable latency, push notifications when the home is offline, and multi-home tenancy. A hybrid is sensible: develop and dogfood over Tailscale while the Azure bridge matures.

## 3. Public API shape: Functions Flex Consumption vs Container Apps vs App Service; can Functions host WebSockets?

### Takeaway
Azure Functions (any plan) is a request/response host: HTTP-triggered functions must respond within 230 s and no Functions doc describes WebSocket hosting, so long-lived WebSockets must terminate in SignalR Service / Web PubSub (or in Container Apps / App Service). The recommended split is REST + negotiate + event handlers on **Functions Flex Consumption (.NET 10 isolated)**, realtime on **Web PubSub or SignalR Service**, and Container Apps only if a Default-mode hub server or the voice relay needs a long-running process.

### Cited Findings

### Inferences
- **Functions cannot be the WebSocket endpoint**; even if a raw upgrade were to work through ASP.NET Core integration, the 230 s front-end limit and scale-to-zero make it unfit. Terminate all client and connector sockets in Web PubSub/SignalR; Functions handles negotiate, REST and webhook events (each a short execution).
- **Cold starts:** a user tapping "lights on" through a scaled-to-zero Flex app pays a cold start on the command path. Set **1 always-ready instance for the `http` group** (covers HTTP, SignalR trigger; Web PubSub triggers are HTTP webhooks too) — cost is the 512 MB or 2 GB baseline GB-s. Keep startup < 30 s (host init timeout).
- **Container Apps** is the right host for anything long-running: a Default-mode SignalR hub server (client results), the realtime voice relay, or an MCP/AI tool server; scale-to-zero is possible but a hub server needs min replicas ≥ 1 (idle-rate billing). The ACA 240 s request timeout applies to HTTP requests; WebSocket support is documented.
- **App Service** offers nothing over ACA here unless the owner already runs a plan; Free/Shared tiers are unsuitable.
- **Recommended public API split:**
  - `api.<domain>` → Functions Flex (.NET 10 isolated, 2 GB, 1 always-ready): `GET /homes/{id}/entities` (from cloud projection), `GET /homes/{id}/state` (snapshot), `POST /homes/{id}/commands` (202 + commandId; optional `?wait=8s`), `GET /commands/{id}`, `GET/PUT /dashboards/{id}` (ETag), `POST /negotiate` (returns Web PubSub client URL with scoped roles), `POST /connectors/pair`, connector-only endpoints (`/connectors/{id}/snapshot`).
  - `wss` → Web PubSub (`clients` hub) for apps/ESP32/TV; `connectors` hub for homes.
  - AI server (ASP.NET Core/Functions, M.E.AI tool calling) calls the same `/commands` API with `wait` semantics (or a service-to-service variant), so policy, audit and idempotency live in one place.

## 4. Cloud-side state: cache/projection of home state; dashboard definitions in cloud vs home

### Takeaway
Yes — keep a cloud projection of last-known state and the device registry so the apps, widgets and the AI server can read instantly and show "home offline since …" instead of failing. Table Storage (or MQTT retained messages if Event Grid is the fabric) is sufficient at household scale; IoT Hub twins are too small for a whole HA state. Dashboards are user data that must sync across devices, so the cloud should be the source of truth with ETag-based optimistic concurrency, mirrored read-only to the connector for LAN-only use.

### Cited Findings
- Event Grid MQTT Retain "stores the last published message on a topic and automatically delivers it to any new subscribers… instantly receive the latest known state"; retained message max 64 KB, expiry up to 365 days. — [mqtt-overview.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/event-grid/mqtt-overview.md), [event-grid includes/limits.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/event-grid/includes/limits.md)
- IoT Hub twin desired and reported sections are max 32 KB each; each property max 4 KB; twin updates 50/s on S1. — [iot-hub-devguide-quotas-throttling.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/iot-hub/iot-hub-devguide-quotas-throttling.md)
- Web PubSub billing counts messages sent to upstream webhooks as outbound traffic (relevant if every state change is also routed to a Function to update the cache). — [concept-billing-model.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/azure-web-pubsub/concept-billing-model.md)
- Service Bus session state can hold up to 256 KB (Standard). — [message-sessions.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/service-bus-messaging/message-sessions.md)

### Inferences
- **Store choice:** Azure Table Storage — PartitionKey = `homeId`, RowKey = `entityId`, columns `state`, `attributes` (JSON, trimmed), `lastChanged`, `version`; separate tables for registry (areas, devices, entity metadata), connector presence (`lastSeen`, `connectionId`, `version`), commands (idempotency/audit), dashboards. Cheap and simple at a few thousand rows per home. Cosmos DB serverless only if you need richer queries/change feed; Redis is unnecessary at this scale (a per-instance in-memory cache in Functions plus Table Storage is enough).
- **Write path without doubling realtime cost:** don't route every state change through a Function. The connector publishes deltas directly to the Web PubSub group (live clients) and **separately** upserts debounced snapshots (e.g. per changed entity, coalesced every 5–30 s, plus a full snapshot on connect) via a batched REST call; numeric sensors only when they pass a deadband. Reads then cost no home round-trip.
- **Staleness contract:** every read returns `asOf` and `homeOnline`; apps show last-known values greyed when the connector is offline; commands fail fast with `HomeOffline`.
- **Source of truth:** HA is the truth for entity state; the cloud is the truth for user-facing configuration (dashboards, favourites, per-user permissions, device-to-home bindings) because it must sync across MAUI, TV and ESP32 and survive Pi/NAS migration. Use ETags (`If-Match`) for conflicts and a monotonic `version`; the connector caches a read-only copy for LAN-only fallback. Dashboard entries reference `entityId`s; when HA renames/removes an entity, the registry sync marks dashboard tiles "missing" rather than deleting them.
- IoT Hub twins (32 KB reported) cannot hold a typical HA instance's full state; they'd fit only presence/version metadata.

### Gaps
- Current Table Storage, Cosmos DB serverless and Azure Cache for Redis prices were not gathered.
- No engineering write-ups of local-first smart-home clouds were found within the tool budget.

## 5. Security: enrolment/pairing, user auth, per-scope authorization, audit, rate limiting, HA token handling, replay protection, multi-tenancy

### Takeaway
Treat the connector as a device with its own identity (keypair or certificate, enrolled through a one-time pairing code shown on the device and confirmed by an authenticated user), issue it short-lived, narrowly scoped transport tokens (Web PubSub roles / SignalR user id / Relay Listen SAS per home), keep the HA token only on the connector, and enforce policy twice — in the cloud API and again on the connector against signed, expiring, idempotent commands — with step-up (biometric confirmation) for locks, alarm and garage.

### Cited Findings
- Web PubSub clients connect with a signed JWT; the `connect` event handler can authenticate, set `userId` and roles, or reject with 401; group-scoped roles `webpubsub.joinLeaveGroup.<group>`, `webpubsub.sendToGroup.<group>` and wildcard patterns limit what each client can do. — [concept-service-internals.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/azure-web-pubsub/concept-service-internals.md)
- SignalR upstream supports authentication settings (token in the `Authentication` header; managed identity), and Key Vault-referenced secrets in upstream URLs. — [concept-upstream.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/azure-signalr/concept-upstream.md)
- SignalR serverless negotiation: the app hosts a negotiate endpoint that issues endpoint URL + access token with a `UserId` (`NegotiateAsync`). — [signalr-howto-use-management-sdk.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/azure-signalr/signalr-howto-use-management-sdk.md)
- Relay listeners need a token with **Listen** right on the namespace or the specific hybrid connection; senders need **Send**; tokens expire and are replaced with a Renew operation. — [relay-hybrid-connections-protocol.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/azure-relay/relay-hybrid-connections-protocol.md)
- Event Grid MQTT auth options: X.509 certificates, Microsoft Entra ID tokens + RBAC, OAuth 2.0 JWT for non-Azure clients, custom webhook authentication. — [mqtt-overview.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/event-grid/mqtt-overview.md)
- IoT Hub provides per-device identity and Device Provisioning Service in all tiers. — [iot-hub-scaling.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/iot-hub/iot-hub-scaling.md)
- Web PubSub event handler webhooks are validated per CloudEvents abuse protection. — [howto-develop-eventhandler.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/azure-web-pubsub/howto-develop-eventhandler.md)

### Inferences
- **Pairing (recommended):** connector generates an Ed25519/ECDSA keypair on first run (private key stays on the Pi/NAS, ideally in a file readable only by the service user) → calls `POST /connectors/enroll` with its public key and gets a short **pairing code** (8 chars, 10-minute TTL, single use, rate-limited) displayed in its local UI/log → the signed-in owner enters the code in the MAUI app (`POST /homes/{id}/pair`) → the API binds `connectorId ↔ homeId ↔ owner`. Afterwards the connector authenticates with a signed JWT assertion (private-key-JWT, like OAuth client assertion) to `POST /connectors/token` and receives a 15–60 min token / Web PubSub URL limited to `userId=connector:<homeId>` and `sendToGroup.home.<homeId>.*`. Re-pairing revokes the old key. This mirrors OAuth device-code UX without depending on Entra for devices. Entra workload identity / client certificates are fine for the owner's own NAS but don't scale to customer homes; Key Vault holds the **cloud's** signing keys and the Web PubSub/SignalR access (or use managed identity), not per-connector secrets.
- **User auth:** reuse the owner's existing JWT auth server (or Entra External ID) for MAUI/TV; ESP32 gets a device-bound refresh token via a pairing code shown on its display or set via the app (BLE/QR), with scopes like `home:read`, `home:control`, `home:sensitive`.
- **Authorization model:** per (user, home) role → scopes; per-domain policy: `sensor/binary_sensor` read; `light/cover/scene/switch/media_player` control; `lock/alarm_control_panel/cover.garage*`, `camera` = sensitive → require a **step-up confirmation token** (short-lived JWT minted after biometric/PIN confirmation in the app, bound to commandId) and never callable by the AI server without explicit user confirmation.
- **Never send the HA token to the cloud:** the cloud speaks an abstract command contract (`entityId`, `service`, `data`, `commandId`); the connector maps it to HA's WebSocket API with its locally stored long-lived token and enforces its own **allow-list** (domains/entities exposed to cloud, sensitive-domain rules), so a compromised cloud or realtime resource cannot call arbitrary HA services (e.g. `shell_command`, `hassio`).
- **Replay protection / integrity:** commands are signed by the API (key in Key Vault; connector pins the public key at pairing) and carry `commandId` (UUID v7), `homeId`, `issuedAt`, `expiresAt` (≈30 s), `actor`, `scope`; the connector rejects expired, wrong-home or already-seen commandIds (LRU/TTL store). This keeps security independent of the transport.
- **Audit:** append-only audit table (or Log Analytics) per command: actor (user/AI/automation), channel, policy decision, step-up used, result, latency; connector echoes the HA context id in the result so cloud audit links to HA's logbook.
- **Rate limiting:** per user and per home on `/commands` (e.g. token bucket 10/s burst 20), stricter for sensitive domains and for AI-originated calls; pairing-code attempts limited per IP/account.
- **Multi-home readiness:** every key, table partition, group name and token scope includes `homeId`; one Web PubSub resource serves many homes via scoped roles; a Relay namespace can hold one hybrid connection per home with per-entity SAS.

### Gaps
- No primary Microsoft guidance specific to pairing home connectors was found; the pairing design is an inference from general patterns.
- Entra External ID pricing/features as of Oct 2026 were not researched.

## 6. Reliability patterns: idempotency, delivery semantics, offline feedback, presence/heartbeat, backpressure

### Takeaway
Use at-most-once delivery with idempotency keys for actuations (convert toggles into absolute set-commands so a retry is safe), explicit timeouts with clear "home offline / timed out / unknown" outcomes, presence from connect/disconnect events plus heartbeats, and server-driven subscription filtering with per-entity coalescing so the state stream stays small.

### Cited Findings
- IoT Hub direct methods return 404 when the device is offline (with `connectTimeoutInSeconds`=0) and 504 when no response within `responseTimeoutInSeconds` (5–300 s). — [iot-hub-devguide-direct-methods.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/iot-hub/iot-hub-devguide-direct-methods.md)
- Relay returns 502 when no listener is connected and 504 after 60 s if the listener does not handle the request. — [relay-hybrid-connections-protocol.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/azure-relay/relay-hybrid-connections-protocol.md)
- Web PubSub `ackId` acks confirm service receipt; the client must await with its own timeout; reliable subprotocol restores sessions via `reconnectionToken` for up to ~1 minute of failures; `connected`/`disconnected` system events are async notifications to the event handler. — [reference-json-webpubsub-subprotocol.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/azure-web-pubsub/reference-json-webpubsub-subprotocol.md), [howto-develop-reliable-clients.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/azure-web-pubsub/howto-develop-reliable-clients.md), [concept-service-internals.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/azure-web-pubsub/concept-service-internals.md)
- SignalR upstream delivers `connected`/`disconnected` connection events (serverless). In Default mode connections drop when their hub server goes offline. — [concept-upstream.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/azure-signalr/concept-upstream.md), [concept-service-mode.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/azure-signalr/concept-service-mode.md)
- Client results: server passes a `CancellationToken` bounding the wait (docs use 30 s). — [AspNetCore.Docs hubs.md](https://github.com/dotnet/AspNetCore.Docs/blob/main/aspnetcore/signalr/hubs.md)
- Event Grid MQTT Last Will and Testament notifies others of abrupt disconnects; persistent sessions keep subscriptions/messages; session expiry 8 h default. — [mqtt-overview.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/event-grid/mqtt-overview.md), [event-grid includes/limits.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/event-grid/includes/limits.md)
- Relay listener Ping keeps NAT mappings alive and detects dead control channels. — [relay-hybrid-connections-protocol.md](https://github.com/MicrosoftDocs/azure-docs/blob/main/articles/azure-relay/relay-hybrid-connections-protocol.md)

### Inferences
- **Delivery semantics:** at-most-once for physical actions by default — the API sends once; if no `ack` from the connector within ~2 s, the result is `Unknown/NotDelivered` and the app re-reads state rather than blindly retrying. Client retries reuse the same `Idempotency-Key` (= commandId), so the API returns the stored outcome instead of re-sending. The connector dedupes commandIds for ~10 min. Make commands **absolute** (`light.turn_on brightness=60`, `cover.set_cover_position 40`) instead of `toggle`, so at-least-once retries are harmless when used (e.g. scenes).
- **Two-stage feedback:** `accepted` (connector received, ≤1 s) and `completed` (HA service call returned, plus the resulting `state_changed` arriving over the stream). UI shows optimistic state, then confirms or reverts; timeouts: 2 s ack, 8–10 s completion (covers/blinds may confirm only via later state changes).
- **Offline handling:** API checks presence before sending; offline → immediate `409/503 HomeOffline` with `lastSeen`; queued commands are **not** executed later by default (stale intent is dangerous), except explicitly "deferred" low-risk commands with an expiry.
- **Presence:** connector connected/disconnected events update the presence row; plus an app-level heartbeat every 30 s (connector → `heartbeat` event or REST) carrying version, HA connectivity and queue depth; offline after 2 missed heartbeats (≈60–90 s) to ride over Web PubSub's reconnect window; also report "connector up, HA down" separately.
- **Backpressure on the state stream:** (1) cloud sends the connector the union of active subscriptions per home (`subscriptions` control message when clients join/leave groups or apps background); (2) connector forwards only those entities; (3) per-entity coalescing — keep only the latest value per entity per window (e.g. 250 ms for lights/covers, 2–5 s for power/temperature, deadband on numeric deltas); (4) drop attribute noise (only whitelisted attributes); (5) bounded outbound queue — on overflow, drop deltas and send a fresh snapshot; (6) on reconnect, send a snapshot version + deltas since that version.
- **Reconnect:** connector uses exponential backoff with jitter and an unbounded retry loop (SignalR's default automatic-reconnect policy gives up after a few attempts — configure a custom `IRetryPolicy`; behaviour not re-verified in this session); Web PubSub reliable protocol recovers short drops without message loss.

### Gaps
- SignalR .NET client automatic-reconnect defaults and stateful-reconnect support with Azure SignalR were not re-verified in this session.
- No measured latency/jitter numbers for Web PubSub/SignalR in Sweden Central were found.

## 7. Local development: Functions host, SignalR/Web PubSub emulators, .NET Aspire

### Takeaway
